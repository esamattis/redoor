# Server logs UI implementation plan

## Goal

Add an authenticated `/logs` UI route that:

- is reachable from the existing burger menu;
- opens a dedicated `/api/v1/server/logs/ws` WebSocket only while the route component is mounted;
- receives the latest 500 complete entries from the active server log file when file logging opened successfully;
- then receives new server log entries live over the same socket;
- renders entries oldest-to-newest in a bounded scrolling region, so the newest entry is at the bottom;
- defaults to auto-scrolling to the bottom and exposes an accessible `Auto-scroll` checkbox to disable/re-enable that behavior;
- retains at most 500 entries client-side as a rolling window, preventing an indefinitely open page from growing memory without bound;
- reconnects while the route remains mounted and replaces its rolling window with a fresh snapshot after reconnect, recovering entries missed during a disconnect.

The implementation must keep historical file access streamed/bounded and asynchronous. It must not read the complete log file into memory or make the existing logger wait for the historical scan.

## Resolved behavior and protocol decisions

1. **No configured/active log file:** the route remains useful. The first WebSocket event reports `file_logging_enabled: false` with an empty history, and subsequent in-process server logs are still streamed live. The UI shows a small explanation that history is unavailable because file logging is disabled.
2. **Log-file open failure:** treat this the same as unavailable file history. `logging::init` already reports the open failure to stderr; the UI must not expose the configured server filesystem path or raw I/O details.
3. **Entry definition:** one formatted logger record is one entry. Live entries use the exact formatted string produced by `logging.rs` (`[timestamp] [LEVEL] message`). Historical entries are newline-delimited records from that same file. Existing calls can technically put newlines inside a message; those continuation lines will be separate historical entries after reconnect. This is a pre-existing format limitation and should be documented in code rather than addressed by changing the log format in this task.
4. **Snapshot/live handoff:** subscription creation must be serialized through the logger task. The logger returns both a broadcast receiver and the exact file byte cutoff after all earlier queued log writes. Read history only through that cutoff; messages after the cutoff arrive through the receiver. This avoids the duplicate/gap race that would result from independently calling file metadata and subscribing.
5. **Slow client behavior:** use a bounded Tokio broadcast channel. If a browser lags beyond its capacity, send a typed `lagged` event if possible and close the socket. The mounted UI reconnects and obtains a new latest-500 snapshot instead of allowing unbounded per-client buffering.
6. **No REST endpoint:** the initial history is sent as the first event on the dedicated WebSocket. Therefore the project rule requiring a dedicated `#[ts(export)]` response for new REST APIs does not apply, but all WebSocket payloads will still be dedicated exported Rust types.

## Detailed implementation steps

### 1. Refactor `src/logging.rs` to support atomic subscriptions

Current structure and constraints:

- `LOGGER` is an `OnceLock<UnboundedSender<LogMessage>>` at lines 8–8.
- `Logger` owns a synchronous `std::fs::File` at lines 36–42.
- `Logger::new` synchronously opens the optional file at lines 44–80.
- `Logger::write` formats, prints, and writes one line at lines 82–101.
- `Logger::run` batches messages from the unbounded input lane at lines 103–116.
- `init` starts the task at lines 119–131 and `log` enqueues without blocking at lines 133–136.

Refactor file access to `tokio::fs::File` and `tokio::io::AsyncWriteExt`, because project rules require Tokio async APIs. Keep `log!` and `logging::log` synchronous/non-blocking for all existing call sites; only startup initialization becomes async.

Introduce these concepts (names can follow this sketch exactly):

```rust
const LIVE_LOG_CAPACITY: usize = 1_024;

/// Commands are serialized with writes so a subscription has an exact history/live boundary.
enum LoggerCommand {
    Write(LogMessage),
    Subscribe {
        reply: tokio::sync::oneshot::Sender<LogSubscription>,
    },
}

/// Handle stored globally so normal logging stays non-blocking while subscriptions can await setup.
struct LoggerHandle {
    commands: mpsc::UnboundedSender<LoggerCommand>,
}

/// Captures the stable file prefix and live receiver created at the same logger queue position.
pub struct LogSubscription {
    pub log_file_path: Option<std::path::PathBuf>,
    pub history_end: u64,
    pub receiver: tokio::sync::broadcast::Receiver<String>,
}

/// Returned when the logger task is unavailable during WebSocket subscription setup.
#[derive(Debug, thiserror::Error)]
pub enum SubscribeError {
    #[error("logger command channel is closed")]
    LoggerClosed,
    #[error("logger dropped the subscription response")]
    ResponseDropped,
}
```

All new functions, structs, enums, and methods need doc comments explaining why they exist, per `AGENTS.md`.

Change `Logger` to own:

- `log_file_path: Option<PathBuf>` only when the file actually opened;
- `log_file: Option<tokio::fs::File>`;
- `log_file_position: u64`, initialized from async file metadata after opening in append mode;
- `live_entries: tokio::sync::broadcast::Sender<String>`;
- the existing level.

Make `Logger::new(log_file_path)` async. Open with `tokio::fs::OpenOptions`, preserving create+append behavior from lines 48–53. If opening or initial metadata fails, emit the existing actionable stderr diagnostic and set active path/file to `None`; do not advertise unusable history to the UI.

Make the write path async and preserve ordering:

```rust
/// Writes one accepted entry before publishing it so the history cutoff always trails durable output.
async fn write(&mut self, level: Level, message: String) {
    if level < self.level {
        return;
    }

    let timestamp = chrono::Local::now().format("%Y-%m-%d %H:%M:%S%.3f");
    let formatted = format!("[{}] [{}] {}", timestamp, level.as_str(), message);
    println!("{}", formatted);

    if let Some(file) = self.log_file.as_mut() {
        let mut bytes = formatted.as_bytes().to_vec();
        bytes.push(b'\n');
        match file.write_all(&bytes).await {
            Ok(()) => self.log_file_position += bytes.len() as u64,
            Err(error) => {
                // Keep the existing stderr-only error behavior; do not recursively call log! here.
                // Consider disabling file history after a failed write so the cutoff cannot become misleading.
            }
        }
    }

    // No active receivers is normal; logging must never fail because nobody is viewing the route.
    let _ = self.live_entries.send(formatted);
}
```

Do not use a `BufWriter` unless subscription handling flushes it before returning `history_end`; otherwise the second file handle used for history may not see accepted entries. Direct `write_all` is simpler for this task.

Update the logger loop to receive `LoggerCommand`. Preserve batching only if it remains clear; correctness is more important than `recv_many`. A subscription arm must execute in queue order:

```rust
LoggerCommand::Subscribe { reply } => {
    let subscription = LogSubscription {
        log_file_path: self.log_file_path.clone(),
        history_end: self.log_file_position,
        receiver: self.live_entries.subscribe(),
    };
    let _ = reply.send(subscription);
}
```

Create the broadcast receiver inside this command arm, not before enqueueing the request.

Change the global API:

```rust
/// Initializes the process-global logger before any log macro is used.
pub async fn init(log_file_path: Option<String>) {
    if LOGGER.get().is_some() {
        return;
    }

    let (commands, receiver) = mpsc::unbounded_channel();
    let logger = Logger::new(log_file_path.map(PathBuf::from)).await;
    let handle = LoggerHandle { commands };
    if LOGGER.set(handle).is_err() {
        return;
    }
    tokio::spawn(logger.run(receiver));
}

/// Establishes an ordered history/live boundary without blocking normal log producers.
pub async fn subscribe() -> Result<LogSubscription, SubscribeError> {
    let logger = LOGGER.get().ok_or(SubscribeError::LoggerClosed)?;
    let (reply, response) = tokio::sync::oneshot::channel();
    logger.commands
        .send(LoggerCommand::Subscribe { reply })
        .map_err(|_| SubscribeError::LoggerClosed)?;
    response.await.map_err(|_| SubscribeError::ResponseDropped)
}
```

`init` has a theoretical concurrent-initialization race if two callers invoke it simultaneously. In this application, startup initializes once before spawning work. Keep the implementation simple, but ensure a losing temporary logger task is not spawned. Constructing before `LOGGER.set` is safe; spawn only after a successful set. If ownership makes that awkward, store the sender first and spawn exactly once inside an async initialization helper guarded by an async once primitive. Do not silently replace the active logger path.

Update `log` at lines 133–136 to send `LoggerCommand::Write(...)` through `LoggerHandle.commands` while retaining its current immediate return behavior.

#### Stream a bounded historical snapshot

Implement an async helper with a concrete contract:

```rust
/// Reads complete newline-delimited entries through `history_end`, retaining only the newest 500.
async fn read_latest_entries(
    path: &std::path::Path,
    history_end: u64,
) -> std::io::Result<Vec<String>>
```

Use:

- `tokio::fs::File::open`;
- `tokio::io::AsyncReadExt::take(history_end)` so appends after subscription cannot leak into the snapshot;
- `tokio::io::BufReader` and `AsyncBufReadExt::lines()`;
- `VecDeque<String>` capped at `HISTORY_ENTRY_LIMIT`, popping the front before pushing once full.

This scans the file asynchronously but retains only 500 entries, so it never loads the complete file into memory and yields while disk reads are pending. It also keeps Axum control requests responsive while a large historical file is scanned. A reverse-tail reader would reduce disk I/O but is substantially more error-prone around UTF-8 and partial final lines; do not introduce it in this implementation.

If `log_file_path` is `None`, return an empty snapshot with `file_logging_enabled: false`. If opening/reading the active file fails after subscription, log the full error server-side and send an empty snapshot with `file_logging_enabled: true` followed by closing the socket (or send an internal-error close frame). Do not put the path or raw error into the browser payload.

There is an unavoidable memory cost for a single extremely long entry because the requested unit is a complete entry. The implementation remains bounded by 500 entries rather than total file size. Do not truncate silently unless a separate product limit is agreed.

#### Socket sequencing

`handle_server_logs_socket` should:

1. call `logging::subscribe().await` immediately;
2. read only `subscription.log_file_path` through `subscription.history_end`;
3. serialize and send `ServerLogEvent::Snapshot` before any live events;
4. split the socket and use a small-arm `tokio::select!` between dedicated helpers for outbound live entries and inbound disconnect detection, following the project rule at `AGENTS.md`;
5. drop the broadcast receiver when either side completes, removing all backend work for that route connection.

Sketch:

```rust
async fn handle_server_logs_socket(socket: WebSocket) {
    let subscription = match logging::subscribe().await {
        Ok(subscription) => subscription,
        Err(error) => {
            log!(Level::Error, "Failed to subscribe server log websocket: {error}");
            return;
        }
    };

    let entries = match &subscription.log_file_path {
        Some(path) => match read_latest_entries(path, subscription.history_end).await {
            Ok(entries) => entries,
            Err(error) => {
                log!(Level::Error, "Failed to read server log history: {error}");
                Vec::new()
            }
        },
        None => Vec::new(),
    };

    let (mut sender, mut receiver) = socket.split();
    if !send_event(
        &mut sender,
        &ServerLogEvent::Snapshot {
            entries,
            file_logging_enabled: subscription.log_file_path.is_some(),
        },
    )
    .await
    {
        return;
    }

    let mut live_entries = subscription.receiver;
    tokio::select! {
        _ = forward_live_entries(&mut sender, &mut live_entries) => {}
        _ = wait_for_disconnect(&mut receiver) => {}
    }
}
```

Keep `send_event`, `forward_live_entries`, and `wait_for_disconnect` separately documented. Do not log every connection at info level solely to facilitate tests; the Playwright test can generate a real server log through the existing agent WebSocket error path.

In `forward_live_entries`:

- `Ok(entry)` => send `ServerLogEvent::Entry`;
- `RecvError::Closed` => return;
- `RecvError::Lagged(skipped)` => send `ServerLogEvent::Lagged { skipped }`, then return so the browser reconnects and refreshes its window.

Avoid calling `log!` for serialization/send failures that can be caused by this same socket unless recursion is clearly impossible. Serialization of the known enum should be infallible; on failure, report once and terminate.

Message handling:

- ignore non-string frames;
- parse as `ServerLogEvent` in a `try/catch`;
- `snapshot`: replace entries, assigning local IDs in source order; set file logging flag and connected state;
- `entry`: append and retain only `MAX_LOG_ENTRIES` (`next.slice(-MAX_LOG_ENTRIES)`);
- `lagged`: show a short status such as `Live logs fell behind; reconnecting…` and close the socket so the close handler reloads a fresh snapshot;
- malformed events: show a protocol error and close/reconnect instead of rendering unsafe data.

Do not use TypeScript non-null assertions. Narrow refs/socket values explicitly.

## Ambiguities and risks to retain in implementation notes

- **Multiline messages:** current logger output is line-oriented but `message` can contain newlines. Live delivery treats the formatted call as one entry; file history treats each physical line as an entry. Achieving perfect reconnect identity would require a structured/escaped log format and migration strategy, which is outside this task.
- **No-file semantics were unspecified:** this plan chooses empty history plus live process logs, rather than hiding/disabling the route. This preserves utility while accurately labeling that persistent history is unavailable.
- **Large historical files:** the proposed forward async scan is memory-bounded but reads the full file to find its last 500 lines. It keeps Tokio/control work responsive but can consume disk bandwidth. A backward UTF-8-safe tail reader is a future optimization if production log sizes make this material.
- **Single huge entry:** retaining complete entries means one pathological line can still be large. A byte truncation policy was not requested and would change displayed content.
- **Broadcast lag:** a sufficiently busy logger can outrun a browser during snapshot loading. Bounded lag detection plus reconnect prevents memory growth and eventually restores the latest 500, but the UI may briefly reconnect repeatedly under sustained extreme volume.
- **Global logger initialization:** making `init` async touches five existing call sites. The global `OnceLock` also means unit tests should test logger internals directly rather than attempt multiple global configurations in one test process.
- **Playwright fixture age:** other suites can append normal server logs after startup. Assertions should rely on the newest unique fixture being present and the oldest being absent, while exact 500-entry behavior remains covered by deterministic Rust tests.
