# Flaky tests
- 2026-10-22 `pn test` integration (`tests/terminal.test.ts`): `dedicated terminal tunnel > reports the shell's exit status after its last output` failed at line 334 because the lifecycle events were empty (`expected [] to deep equally contain { type: "exit", code: 3, signal: null }`). All 5 tests in the file passed on immediate rerun. Investigated 2026-10-29: 12 loaded runs of the file and 300 loaded repeats of the test all passed. Every way the agent side of the server relay can end sends an exit or error frame before closing, so an empty lifecycle needs the browser half of the relay to stop first (a browser frame the server rejects) or the server to go away. The likeliest cause is a concurrent `pn playwright` whose `preplaywright` hook then killed every listener on the reserved vitest port (fixed the same day: each hook now frees only its own suite's port). The assertion now reports the close code (1006 = socket dropped, 1005 = relay's own close) and the output, so the server log in `./log` plus that code should pin it down if it recurs.
- 2026-10-29 `pn test` integration (`tests/git.test.ts`): `Git browser REST API > reports conflicts, non-UTF-8 omissions, and deterministic truncation while control stays responsive` failed at line 520 because the slow status finished before the echo control command (`expected 'status' to be 'echo'`). It ran while the Playwright suite loaded the machine in parallel. All 9 tests in the file passed on immediate rerun. Seen during a UI-only change (issue #14), so it is not caused by that change.
- 2026-10-29 `pn test` integration (`tests/git.test.ts`): `Git browser REST API > reports conflicts, non-UTF-8 omissions, and deterministic truncation while control stays responsive` failed again at line 520 with `expected 'status' to be 'echo'`, while Playwright ran in parallel. The full `pn test` passed on immediate rerun. Seen during a UI-only change (issue #16), so it is not caused by that change. This is the second time this test has been flaky. Investigated 2026-10-29: not a server or agent bug. The agent spawns every command as its own task and runs Git work in `spawn_blocking`, so an echo never queues behind a status walk; the agent log showed the echo arriving after the status had already finished. The test relied on a status over 5,001 untracked files being slow, but that walk takes about 25 ms, which is shorter than the echo's HTTP and websocket round trip when Playwright loads the machine. The test now replaces `.git/info/exclude` with a FIFO: the agent's status blocks opening it until the test opens the write end, the test sends the echo while the status is held and only then closes the gate. 30 runs of the file under Playwright plus 8 busy-loop CPU burners (load average 16) all passed.
